# doge-code OpenRouter 対応とモデル切替 詳細設計

- 状態: 承認済み。実装は未着手。
- 作成日: 2026-10-22
- 設計担当: Astra
- 将来の実装担当: Codex（gpt-6.1-sol）
- 対象リポジトリ: mopemope/doge-code
- 格納予定先: docs/superpowers/specs/2026-10-22-openrouter-model-selection-design.md

本書は、承認済みの構成方針を実装可能な詳細仕様に定めたレビュー用文書である。専用 provider と既存モデル選択 UI の拡張により OpenRouter を利用できるようにする。モデル切替では新しい会話を作成し、元の履歴と未送信入力を保護する。構成方針の承認と本書の詳細仕様の承認は区別する。本書のレビュー完了前に実装へ進まない。実装計画は本書の承認後に作成する。

## 1. 目的と承認済みの方針

1. OpenRouter 専用 provider を追加し、CLI とモデル検索画面の両方からモデルを指定・選択できるようにする。
2. モデルを切り替えるときは新しい会話を開始する。切替前の会話履歴、保存済みセッション、未送信入力を保持する。
3. OpenRouter の認証情報は OpenAI、OpenCode、OAuth の認証情報から分離する。
4. モデルを暗黙に選ばない。失敗を契機に別モデルへ切り替えたり、別の課金経路へフォールバックしたりしない。
5. 一覧の閲覧、検索、モデル選択だけでは推論リクエストを送らない。

利用者が承認済みなのはこの構成方針であり、以下の詳細仕様はレビュー対象である。

## 2. 前提と対象範囲

- 実 API キーや有料推論を使う動作試験。

## 3. CLI と TUI の利用契約

### CLI

- `dgc models --provider openrouter` は OpenRouter のモデル一覧を表示する。
- `dgc models --provider openrouter --model publisher/model` は、その完全な ID をカタログ内で厳密に検索し、詳細を表示する。大小文字を変更せず、該当しない場合は非ゼロ終了する。このコマンドでは推論しない。
- `--refresh` はカタログの取得を明示的に要求する。
- `--offline` はカタログのネットワーク取得を禁止する。
- `--refresh` と `--offline` の併用はエラーとする。この二つのフラグを OpenRouter 以外に指定した場合も、未対応であることを明示してエラーとする。
- 通常起動の `--provider openrouter --model publisher/model` と exec での同等の指定をサポートする。
- 既定のモデルは用意しない。必要な場面でモデルが未指定なら、モデル一覧と明示指定の方法を示して終了する。
- 明示的なセッション再開では、保存済みモデルをクライアント生成前に復元する。指定した再開対象が見つからない場合、新しい会話へ黙って切り替えない。

カタログ内の厳密な詳細検索と、カタログに未掲載の ID を直接指定して推論を試みる操作は別である。後者は第 5 節と第 7 節の契約に従う。

### TUI

- `/provider openrouter [検索語]` で OpenRouter の選択画面を開く。
- OpenRouter 利用中の `/models [検索語]` も同じ選択画面を開く。
- 既存の Go/Zen の操作は維持する。
- 引数なしの `/provider` は、現在の provider が Go、Zen、OpenRouter のいずれかならその provider をプレビューし、それ以外では従来どおり Go をプレビューする。
- Tab は Go → Zen → OpenRouter の順、Shift+Tab は逆順にプレビュー対象を切り替える。
- 矢印キーで候補を移動する。Enter は選択したモデルで新しい会話を開始する。
- Esc、Ctrl+C、Ctrl+G はキャンセルする。
- Ctrl+R は OpenRouter カタログを更新する。Go/Zen では固定カタログである旨を表示し、更新処理はしない。

閲覧、検索、プレビュー、Enter による選択では推論を送らない。切替はセッション内の選択であり、グローバル設定を書き換えない。未送信入力は切替後も保持する。

## 4. Provider と設定および認証情報の分離

### Provider と接続先

- enum に `ProviderKind::Openrouter` を追加する。
- CLI、TOML、`DGC_PROVIDER` の値は `openrouter` とし、別名は追加しない。
- 固定ベース URL は `https://openrouter.ai/api/v1` とする。
- 推論先は `/chat/completions`、カタログ取得先は `/models` とする。
- URL は文字列の前方一致ではなく、構文解析して検証する。HTTPS、正確なホスト名、実効ポート 443、所定のパスを要求し、ユーザー情報、クエリ、フラグメントを認めない。ホスト名の大小文字と末尾のスラッシュは正規化する。
- 明示された別のベース URL はエラーにし、カスタム接続先には汎用 openai-compatible を使うよう案内する。
- 今回は `OPENROUTER_BASE_URL` を追加しない。
- リダイレクトを追従しない。

### API キーとモデルの解決

API キーの優先順位は次のとおりとする。

1. CLI の `--api-key`。
2. `OPENROUTER_API_KEY`。
3. 同じ設定ソースで provider が明示的に openrouter に設定されたプロジェクト設定。
4. 同じ設定ソースで provider が明示的に openrouter に設定されたユーザー設定。

モデルの優先順位も同じ構造とし、環境変数には `OPENROUTER_MODEL` を使用する。空文字・空白のみの値は未設定として扱う。再開時の保存済みモデルの優先は第 9 節に従う。

`OPENAI_*`、`OPENCODE_*`、OAuth の資格情報は流用しない。provider 未指定の設定ソースからキーやモデルを継承しない。OpenRouter 環境変数が存在するだけで provider を OpenRouter に変更しない。

### TUI での切替

- OpenRouter 内でのモデル切替では、現在のキーとその取得元を保持する。
- 別 provider から OpenRouter への切替では、現在のプロセスの `OPENROUTER_API_KEY` のみを利用する。他 provider の設定値や保存キーは流用しない。
- キーがなくてもカタログ閲覧と新しいセッションの作成は許可する。推論時はキー不足を明確に通知し、環境変数の設定と再起動を案内する。
- UI の「キー設定済み」は値の存在のみを示す。キーの有効性や残高を確認済みとは表示しない。

## 5. モデル ID とカタログ取得およびキャッシュ

### モデル ID

モデル ID は 1〜256 バイトとし、ASCII 英数字と `-_.~:/` のみを許可する。スラッシュを含み、その両側が空でないことを要求する。空白、制御文字、クエリ、フラグメント、ユーザー情報を許可しない。

publisher、モデル名、サフィックスを含む ID 全体をそのまま保持する。明示されたルーティング用 ID は受け付けるが、そのサーバー側の選択規則まで固定モデルであるとは保証しない。クライアントによる ID の置換やフォールバックモデル一覧の生成は行わない。

### カタログのデータ

カタログモジュールは、HTTP 取得、解析、キャッシュを推論クライアントから分離する。扱う情報は次のとおりとする。

- ID と表示名。
- 入出力モダリティ。
- `supported_parameters`。
- コンテキスト長。
- prompt、completion、request の価格。
- 条件付き価格・価格上書きの存在。
- reasoning のメタデータ。

省略された任意項目は不明として扱い、false や 0 を補わない。たとえば `supported_parameters` が存在して tools を含まない場合は tools 非対応、項目自体がない場合は対応不明とする。出力モダリティも同様に、確認できた値と不明を区別する。

### 取得の上限と失敗条件

| 項目 | 上限・契約 |
| --- | --- |
| 接続タイムアウト | 5 秒 |
| 全体タイムアウト | 10 秒 |
| 試行回数 | 操作ごとに 1 回 |
| リダイレクト | 追従しない |
| 応答サイズ | 展開後 8 MiB |
| data の件数 | 10,000 件 |
| ID | 256 バイト |
| 表示名 | 256 Unicode scalar values |
| 価格文字列 | 128 バイト |

HTTP 非 2xx、不正な外側の JSON 構造、サイズ超過、件数超過、重複 ID は更新全体を失敗させる。不正な ID の項目は除外し、除外件数を表示する。任意項目の型不正はその項目を不明として扱う。正規化後に有効な項目が一件もない場合は失敗とし、正常な既存キャッシュを上書きしない。

表示時には制御文字を除く。取得した値をパス、シェル入力、書式文字列として扱わない。

カタログは公開 GET とし、Authorization、Cookie、推論用ヘッダー、プロンプト、プロジェクトのパスを送らない。公式資料には匿名 GET の例があるが、本設計作成時に実接続での匿名取得成功までは検証していない。必要な追加確認は公開情報への読み取りのみとし、失敗しても認証付き取得へ自動変更しない。

### キャッシュ

- 保存先は OS のユーザーキャッシュディレクトリ配下の `doge-code/openrouter/models-v1.json` とする。
- スキーマバージョン、固定の取得元識別子、UTC の取得時刻、正規化した公開メタデータのみを保存する。
- TTL は 24 時間とする。現在時刻より 5 分を超えて未来の取得時刻は無効とする。
- 通常の期限切れデータは stale として使用できる。
- キャッシュの読み込み上限も 8 MiB とする。解析不能、異なるスキーマ、異なる取得元はキャッシュなしとして扱う。
- 同じディレクトリの一時ファイルから atomic rename で更新する。
- 書き込み失敗時も取得済みのメモリ内スナップショットは利用し、保存できなかった旨を警告する。
- キャッシュディレクトリを得られない場合は、メモリ内だけで動作する。

通常の一覧操作では fresh キャッシュを即時利用する。キャッシュなしまたは stale の場合は 1 回取得し、失敗時に stale があれば警告付きで利用する。`--refresh` は常に 1 回取得する。`--offline` はキャッシュだけを使用し、利用可能なキャッシュがなければ非ゼロ終了する。

起動、セッション再開、推論のためだけにカタログ HTTP を暗黙に送らない。これらは既存キャッシュのメタデータだけを参照する。

## 6. モデル選択画面の状態と表示

### 共通 DTO と状態

モデル選択画面の候補は所有権を持つ共通 DTO にする。Go/Zen の静的カタログは表示用に変換するだけとし、接続経路や認証処理は変更しない。

状態は次の五つとする。

| 状態 | 表示・操作 |
| --- | --- |
| ReadyFresh | fresh な候補を表示し、選択できる |
| LoadingWithoutSnapshot | 候補なしで取得中。Enter は無効 |
| RefreshingWithSnapshot | 既存候補を表示したまま更新中。閲覧・絞り込みは可能、Enter は無効 |
| ReadyStale | stale な候補と警告を表示し、選択できる |
| FailedWithoutSnapshot | 候補を表示できない理由と再試行操作を表示する |

stale キャッシュがあるときは表示を保ったまま取得する。取得完了または失敗後の選択には、あらためて Enter を押す必要がある。更新中のキー入力を予約して自動選択しない。

カタログ処理は既存 JobManager で管理し、ジョブの終了処理を済ませてからモデル選択を可能にする。閉じる操作と provider のプレビュー変更で取得をキャンセルする。世代 ID によって、以前の画面に対する遅延結果を破棄する。

自動更新タイマーは追加しない。再試行は Ctrl+R または次回の画面表示時に行う。検索キー入力のたびにネットワーク取得しない。

### 検索と選択可能性

- 検索は ID と表示名に対するローカルの大小文字を区別しない部分一致とする。
- ID の完全一致を先頭にし、それ以外は ID 順に並べる。
- 現在のモデルが候補にあれば初期選択にし、なければ先頭を選択する。
- text 出力と tools の両方への対応が確認できた項目だけを選択可能にする。
- 非対応または不明の項目は理由を表示して選択不可とする。
- カタログで能力が不明な ID を、利用者が CLI で明示的に指定することは許可する。

### 表示内容

provider 名と従量課金であること、ID・表示名、キーの有無、能力、コンテキスト長、価格、取得時刻と fresh/stale/offline の状態を表示する。Enter が新しい会話を作ることと、キャンセル方法を明示する。

価格は USD の参考値であり、有限かつ非負の数値だけを表示用に解釈する。request 単位や条件付き料金があることも示す。不明を 0 として扱わず、実請求額の推計や無料の保証には使わない。

## 7. 推論経路とツール実行の契約

### 経路とリクエスト

OpenRouter 専用 provider は常に Chat Completions を使用する。既存の公式 OpenAI の暗黙 Responses、明示的な openai-compatible の Chat、汎用の OpenRouter カスタム URL、OAuth、Go/Zen の経路は維持する。

agent と subagent は既存の検証付き非ストリーミングループを利用する。リクエストの provider とモデルは開始時のスナップショットに固定する。ツールを使う要求には `provider.require_parameters=true` を設定する。

`models` によるフォールバック一覧、`reasoning.mode=pro`、Web 用の有料アドオンを追加しない。対応不可が既知ならローカルで拒否する。能力が不明な明示 ID はリモートの検証に委ね、モデル名の系列だけから能力を推測しない。

既存のツールカタログとローカル検証を必ず通す。`require_parameters` を設定しただけで、ネストした strict schema の遵守まで保証されるとは扱わない。

OpenRouter の同一モデル内における通常のホスティング事業者ルーティングは変更しない。これは dgc が別モデルや別課金経路へ切り替える機能とは区別する。

OpenCode 専用ヘッダーや OAuth 専用ヘッダーを OpenRouter に送らない。

### レスポンスとツール検証

HTTP 成功だけでは推論成功としない。エラー形式の応答は型付きエラーにする。assistant role、終了状態、内容、ツール呼び出しを検証する。

- 通常の最終応答は空白だけでない内容を要求する。
- ツール呼び出しだけの応答では null content を許可する。
- ツールの ID、種類、カタログへの存在、引数をバッチ全体で検証してから実行する。
- 一つでも不正なツール呼び出しがあれば、同じバッチの他のツールも実行しない。
- length、content_filter、error、refusal、不完全な終了、空の最終応答を正常完了にしない。
- Responses の opaque provider state を OpenRouter Chat に受け渡さない。
- 未知の追加メタデータは無視できるが、失敗を示す状態は無視しない。

### ストリーミングの扱い

OpenRouter の `run_agent_streaming_once` は標準の検証付き agent loop に委譲する。テキスト用 `chat_stream` は、非ストリーミング応答を最後まで取得・検証してから一つの項目として返す。

今回はネイティブ SSE を追加せず、汎用 SSE パーサーも変更しない。途中で組み上がった引数からツールを実行しない。トークン単位のストリーミング対応とは表示しない。

既存のキャンセルとタイムアウトは利用するが、キャンセルによって提供側の生成や課金まで必ず止まるとは保証しない。

## 8. Reasoning の指定と履歴の保存

既存の `ReasoningPayload` を利用する。OpenRouter の effort ヒントは `reasoning.effort` に変換し、汎用 provider の形式は変更しない。

- Auto は、要求する effort の対応をメタデータで確認できる場合だけ送る。非対応または不明なら省略し、より高い effort へ変更しない。
- Fixed は、既知の非対応値ならエラーにする。不明なモデルでは利用者の明示指定として送信し、リモートの検証に委ねる。
- Off はヒントを送らないことを意味し、モデルの thinking を必ず無効にすることは意味しない。
- `supported_efforts` が明示的に null の場合はゲートウェイの effort 値を許容するというメタデータとして扱い、項目がない場合は不明とする。
- mandatory が true のモデルに対し、自動的に none を指定しない。

`reasoning_details` の JSON 配列、順序、暗号化済みデータを変更せず保持する。`reasoning` と `reasoning_content` の両方の応答を受け付け、両方に非 null の値がある場合は `reasoning_content` を優先し、それ以外は `reasoning` を使用する。この正規化はテキストの別名にだけ適用し、details を書き換えない。リクエスト側は既存の、OpenRouter が受け付ける `reasoning_content` の別名形式を使用する。

reasoning の詳細をログに出さない。assistant の reasoning と対応するツール結果の往復を保持する。未完了の現在のツールブロックを compaction で切断せず、既存の復元可能性を保つ。OpenRouter 専用の履歴削除処理は追加しない。

## 9. セッション切替と再開の整合性

### 保存情報

起動、新規作成、モデル選択、exec の各経路で、provider とモデル ID 全体をセッション選択情報として保存する。

OpenRouter の inference binding は、provider、正規化したベース URL、Chat、モデル ID 全体で構成する。キー、キーのハッシュ、アカウント情報を含めない。

### 切替の順序

1. 実行中ジョブ、待機中の追加指示、diff レビューがある場合は切替を拒否する。
2. 選択先とメタデータを検証する。
3. 候補の設定、クライアント、キー解決結果を準備する。
4. 失敗し得るロック取得を行う。
5. 元の会話を flush し、新しいチェックポイントを保存する。
6. 設定、クライアント、ツール、UI の切替を公開する。
7. 新しい履歴とターン状態を開始し、未送信入力を維持する。

コミット前に失敗した場合、現在のランタイム状態と元のチェックポイントを変更しない。atomic rename 後の fsync のように永続化の確実性だけが不明な場合は、既存の durability warning として扱い、誤ったロールバックをしない。

Enter のキーリピートによる二重切替を無視する。過去セッションを整理・削除しない。使用量カウンターは共有できるが、既存ジョブの provider・モデルのスナップショットを書き換えない。

### 再開

保存済みモデルは同じ provider 内で起動時のモデルより優先する。異なる起動モデルを理由に保存済みモデルを書き換えない。異なる provider での再開は明示的なエラーにし、自動的に provider を変更しない。

従来の汎用 openai-compatible で OpenRouter を使っていたセッションは、元の互換経路で再開する。専用 provider へ自動移行しない。他モデルや他 provider の opaque state を再利用しない。

不一致は、可能な限りクライアント生成、推論、セッション変更の前に拒否する。キー未設定時もこの整合性検証を省略しない。

## 10. 能力メタデータとコンテキストおよび使用量

ランタイムには provider、完全なモデル ID、取得時刻に結び付いた不変のメタデータスナップショットを必要に応じて保持する。カタログ全体をセッションや設定ファイルへ埋め込まない。

コンテキストの判定順序は次のとおりとする。

1. 利用者による明示的なコンテキスト設定。
2. provider とモデル ID が完全一致する、正のカタログ値。
3. 不明として扱い、既存の fallback estimate を使用する。

fallback estimate は内部の処理上の見積もりであり、そのモデルの実際の容量とは表示しない。切替時は以前のモデルのメタデータを捨てる。再開時は既存キャッシュだけを使い、利用できなければ不明とする。カタログ更新によって実行中リクエストの条件を変更しない。

任意の usage 項目が欠けている場合は不明のままとし、0 と見せかけない。実請求額を独自計算しない。

## 11. エラーと再試行およびログ

エラーは安全な固定メッセージで分類する。

- キー不足: OpenRouter 用キーの設定と再起動を案内する。
- 不正な接続先: 専用 provider の固定 URL と汎用 provider の利用方法を案内する。
- モデル不足: 一覧と明示指定を案内する。
- 401: 認証エラー。
- 402: 残高・予算に関するエラー。
- 403: アクセス拒否。
- 404: モデルまたは能力に関する利用不可。
- 429: レート制限。
- 5xx: サービス側エラー。
- 不正な応答、不完全な応答、拒否応答: 正常完了と区別する。

カタログ取得エラーによって現在の会話を変更しない。既存の retry、backoff、Retry-After、キャンセル処理のみを利用し、401・402・403・404 に新しい再試行を追加しない。HTTP 200 内のエラーを自動再送しない。

ログには HTTP ステータス、安全なエラーコード、許可されたリクエスト ID のみを含める。応答本文、提供側の自由文、プロンプト、キー、reasoning、ツール引数を出さない。

## 12. 実装境界

以下は責務の分割であり、着手順やコミット単位を定める実装計画ではない。

- `src/features/openrouter/` に `mod.rs`、`catalog.rs`、テストを追加する。専用 provider の設定・リクエスト補助と、独立したカタログ処理を担当する。
- 既存の model_selection は所有権を持つ DTO と小さな共通選択ヘルパーを担当する。
- config は provider ごとの設定スコープ、キー分離、ランタイムのメタデータを担当する。
- llm は OpenRouter のリクエスト変換、検証付きバッファ応答、セッション binding を担当する。
- TUI はカタログジョブ、描画、キーイベント、原子的なセッション選択を担当する。
- main と exec は CLI の一覧操作、起動時選択、再開の整合性を担当する。

`opencode::default_base` は OpenCode 専用のままにする。OpenRouter を追加して、OpenCode の認証共有、ヘッダー、経路判定へ誤って入れない。

新しい依存は追加しない。既存の reqwest、tokio、serde、dirs、tempfile、chrono、JobManager を利用する。

## 13. 受け入れ条件と検証範囲

### 自動検証で満たす条件

- CLI、TUI、exec、再開で、本書のモデル選択契約が成立する。
- PR #177、OAuth、Go/Zen、汎用 openai-compatible の経路を維持する。
- キーが provider 間で混ざらず、閲覧・選択時に推論しない。
- 隠れたモデル選択、課金経路変更、モデルフォールバックがない。
- 完全なモデル ID とサフィックスを保持する。
- キャッシュ上限、解析不良、書き込み失敗、stale fallback、キャンセル、遅延結果の破棄を検証する。
- キーなし閲覧とキーなし推論エラーを区別する。
- reasoning とツール結果の往復、バッチ全体のツール検証を確認する。
- エラー、refusal、不完全な応答を成功扱いしない。
- README、CLI help、TUI help の説明と実装が一致する。
- リポジトリの既存検証ゲートを満たす。

合成の認証値、一時 HOME、一時 config/cache/project、ローカル HTTP フィクスチャを使用する。実際のキー、利用者の設定、有料推論は使用しない。

### TUI の確認

検索、完全 ID の貼り付け、Enter、キーリピート、Esc、再表示、取得中の画面終了、provider プレビュー変更、stale fallback、キーなし状態、狭い画面と未送信入力、処理中の切替拒否を確認する。画面または操作記録で確認結果を残す。

モックで検証した契約と、実サービスで未検証の可用性・品質を区別して報告する。モック通過をライブ動作の保証とはしない。

## 14. 導入とロールバック

OpenRouter 専用 provider は明示的に選んだ場合だけ使われる追加機能とし、従来の汎用互換経路を残す。旧セッションの自動移行はしない。

公開カタログのキャッシュを削除してもセッションを失わない。新しい OpenRouter セッションは古いバイナリでは読めない可能性があるため、ロールバック時もファイルを保持し、必要なら対応する新しいバイナリへ戻す。セッションの provider を書き換えて互換性を偽装しない。

実装の導入は feature branch と PR を経由する。develop へ直接更新しない。

## 15. 自己レビュー

以下の曖昧さを、本書の契約で解消した。

- 既定の有料モデルを置かず、保存済みモデルの再開優先順位を定義した。
- キーなしで可能な閲覧・選択と、認証が必要な推論を区別した。
- provider 間のキー分離と、TUI から切り替える際のキー取得元を固定した。
- カタログ取得の契機、タイムアウト、容量、件数、キャッシュ寿命を定義した。
- 取得中の選択禁止、ジョブ終了処理、世代 ID による古い結果の破棄を定義した。
- 能力不明のモデルについて、picker での選択不可と CLI の明示指定を区別した。
- 同一モデルのホスティング事業者ルーティングと、クライアントによるモデル・課金経路フォールバックを区別した。
- reasoning の別名、同時出現時の優先順位、details の保存を定義した。
- 初期対応は検証付きバッファ応答とし、ネイティブ SSE と誤認させない。
- OpenCode 専用ヘルパーの境界を維持し、認証・ヘッダー・経路の混入を防ぐ。
- カタログとセッションへ秘密情報を保存せず、能力・価格・usage の不明を 0 としない。
- アカウント操作、課金設定変更、有料の実推論試験を含めない。

未解決の設計判断は残していない。実サービスの可用性やモデル品質が未検証であることは、設計上の未決事項ではなく検証範囲の制約である。本書は詳細仕様のレビュー待ちであり、実装計画の作成と実装着手はまだ行わない。
